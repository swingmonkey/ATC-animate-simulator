> 状态：**规范（起草于 v1.7 开发期）** · 适用版本：v2.1+（Step R1 起）
> 定位：本文是 [`docs/PLAN-v2.md`](PLAN-v2.md)、[`docs/FLIGHT-LIFECYCLE.md`](FLIGHT-LIFECYCLE.md)、
> [`docs/WORKPLACE.md`](WORKPLACE.md) 之后的**第四篇配套文档** ——

> 凡涉及"这条规则为什么要这样定、它的现实依据是什么、我们简化到什么程度"的争议，以本文为准。

> 2023-01-01 施行，以下简称"本规则"）。本文所有条号均指该文本重新公布后的**正文条号**。

> **免责声明（重要）**
> - 本文与本项目的全部数值（席位门槛、间隔、休息时长、疲劳阈值、刹车效应等级……）都是**游戏化示意值**，
>   仅用于模拟演示与教学设计，**不得作为真实运行的任何依据**。
> - 本规则正文中的"应当 / 不得 / 必须"是**对真实管制单位与管制员的规范性要求**。本项目**不是**民航运行系统、
>   **不提供**任何可用于真实管制的功能；引用条款只为让模拟更接近现实、让教学口径有据可查。

> - 各管制单位的现场制度、扇区划分、协议内容差异很大，本项目取**典型简化**，差异项集中在数据层便于调整。

## 1. 目标与定位

### 1.1 为什么要单独成文

前三篇文档已经把"怎么分层、航班怎么走、人在哪儿上班"讲清楚了，但留下一个悬空问题：

> **这些设计判断的现实依据是什么？我们到底是"照着规章做"，还是"为了好玩编的"？**

不澄清这一点会带来两个后果：

| 后果 | 表现 |
|---|---|
| **专业性受损** | 玩家（尤其是从业者）发现"塔台可以单人值所有席"、"进近和区调用同一个间隔"，认为项目不懂行 |
| **合规风险** | 读者误以为本项目的数值可以照搬到真实值班制度、间隔配置、席位编制上 |

本文的做法是**逐条列出对照**：规章要求 → 本项目机制 → 游戏化偏离 → 代码落点。
**能对齐的尽量对齐，必须简化的明确标注简化幅度**，不留模糊地带。

### 1.2 三条对齐原则

| 原则 | 含义 | 反面（必须避免） |
|---|---|---|
| **可玩优先** | 规章是设计的**约束与灵感来源**，不是必须逐字实现的验收标准；与现实冲突时选可玩 | 把 249 页规章做成 249 条硬性校验，游戏变成执法考试 |
| **数据化** | 所有可调数值（门槛/间隔/时长）进 `data/` 或 `core/constants.js`，**不硬编码进逻辑** | 把 `40000` 架次门槛、`90 min` 班次写死在 `if` 里，改一个数要翻十个文件 |
| **可追溯** | 每个机制在设计文档里都能指回**条号**；每个数值都能指回**数据字段** | "这数值哪来的"答不上来，日后无法评估是否需要调整 |

### 1.3 合规边界（明确做什么 / 不做什么）

| 类别 | 本项目做 | 本项目不做 |
|---|---|---|
| 席位与编制 | 用**门槛规则**决定游戏内开放哪些席位，让"小机场合并值守 / 大机场分席"可被体验 | 不给出真实编制建议；不按真实架次数据自动生成编制方案 |
| 许可与复诵 | 实现**必背复诵清单**、错诵抽取与纠正链路（教学价值最高的部分） | 不校验完整话术格式；不做真实话音识别 |
| 间隔 | 按**席位分级**呈现间隔标准，做间隔告警与冲突预测 | 不做真实尾流间隔表、不用于真实间隔计算 |
| 值班与疲劳 | 用压缩时间尺度呈现"疲劳 → 休息 → 交接"的**因果链** | 不实现真实排班系统；不做真实健康/合规判定 |
| 记录 | 游戏内**本地**存档、复盘时间轴、练习日志 | **不采集、不上传、不对外提供**任何运行记录（第 69 条） |
| 安全保卫 | 作为**现场层事件**（门禁报警 / 访客登记）呈现 | 不做真实安保系统；不涉及涉密、军事、重大运输任务场景细节 |

## 3. 席位设置门槛规则化（§44–§54）

### 3.1 现状与问题

WORKPLACE §3 的映射表与 §9.4 的 `merge: ['CD','APC','GND']` 是**硬编码示意**：

```js
// 现状（示意）：合并规则写死在数据里，与"为什么这么合"脱钩
seats: [ { id: 'TWR', ... }, { id: 'GND', ... } ]
```

问题：玩家看不出**为什么小机场只有两个席位、大机场有六个**，也无法体验"流量涨了该增席"这一真实管理动作。

### 3.2 规则函数 `domain/seats.js`（层 2，纯函数）

```js
 * @returns {{ tower:string[], approach:string[], area:string[], reasons:object }}
 */
export function planSeats(ops) { /* ... */ }
```

| 规则 | 触发条件（规章） | 游戏内动作 | 常量 |
|---|---|---|---|
| 机场管制席 | **必须**（§47） | 永远开放 `TWR` | — |

## 4. 岗位工作制度三件套（§55–§61）

规章 §57 把岗位工作制度归纳为**三件事**：上岗前准备、岗位交接班、岗后分析讲评。
WORKPLACE 已覆盖后两件（§5.4 交接检查单、§6.4 讲评），**缺上岗前准备**——本节补齐，并把三件套正式定义为值班 FSM 的三段。

### 4.1 值班 FSM（对齐 §57 / §123）

```
        ┌──────────┐   就座    ┌───────────────┐   离席/到点   ┌──────────┐
  开局 │   PREP   │ ────────▶ │  ON_POSITION  │ ───────────▶ │ DEBRIEF  │
        │ 岗前准备 │           │   岗位执勤     │               │ 分析讲评  │
        └──────────┘           └───────────────┘               └──────────┘
             │                        │  ▲
             │ 申请不执勤              │  │ 休息（REST）
             ▼                        ▼  │
        ┌──────────┐              ┌──────────┐
        │ OFF_DUTY │              │ RESTING  │ ← 期间不得安排任何工作（§125）
        └──────────┘              └──────────┘
```

- **`dutySec`（执勤时间，§123）** = `PREP + ON_POSITION + DEBRIEF` 三段之和（+ 培训/其他，本项目暂不实现）
- **`positionSec`（岗位执勤时间，§124）** = 只在 `ON_POSITION` 累加
- **`restSec`（休息时间，§125）** = 只在 `RESTING` 累加，**该状态内所有指挥入口禁用**

> **与 WORKPLACE §5.1 的关系**：短班模式从 `ON_POSITION` 直接开始（跳过 `PREP`，保留 `DEBRIEF`），
> 保证"永久保留"的兼容承诺；整班模式从 `PREP` 开始。

### 4.2 岗前准备 5 项（§59）→ `PREP` 面板

## 5. 管制责任移交与管制协议（§36–§41、§111–§113）

### 5.1 现状与问题

`js/domain/airspace.js` 的移交是**一步到位**的：

```js
export function handoffAircraft(ac, toCode, options = {}) {
    ...
    ac.unit = toCode;              // ← 直接改归属
    ac.unitTarget = toCode;
    ...
}
```

这**违反 §112/§113**：规章要求"未经接受单位同意不得移交""接受方应明确表明是否接受"。
现状下移交是**无条件的单方面动作**，玩家体验不到"移交通不过"这一真实且高频的场景。

### 5.2 移交三要素：请求 / 接受 / 拒绝

```
移交方                          接受方
  │  requestHandoff(ac, to)        │
  │ ──── 移交包（§112）──────────▶ │   ① 进程单快照
  │                                │   ② 高度/速度/意图
  │                                │   ③ 移交条件（高度限制、移交点）
  │                                │
  │ ◀── accept / reject(reason) ── │   §113 明确表明是否接受
  │                                │
  ├─ accept → ac.unit = to（责任转移，§111 单一责任）
  └─ reject → 责任仍属移交方，落 HANDOFF_REJECTED（−2），复盘标出原因
```

**关键状态机**（`ac.unitState`）：

| 状态 | 含义 | `ac.unit` 取值 | 允许操作 |
|---|---|---|---|
| `OWNED` | 正常归属 | 本席位 | 全部 |
| `HANDOFF_PENDING` | 已请求，等待对方答复（示意 5–15 s） | **仍是移交方**（§111） | 仍可下指令、可撤回 |
| `HANDOFF_REJECTED` | 被拒 | 移交方 | 可改条件后重试 |
| `TRANSFERRED` | 接受完成 | 接受方 | 对本席位而言转为只读 |

> **必须保证**：`HANDOFF_PENDING` 期间 **责任不转移**（§111 的"任何时间内只由一个单位承担"）。
> 这是与现状最关键的差别：现状是"改了就转了"，新设计是"答应了才转"。

**AI 接受判据**（示意，走 `core/random.js` 种子）：接受方按**协议是否覆盖 + 移交条件是否满足 + 对方是否给了完整移交包**三项打分，
低于阈值则拒绝并给出原因（"高度不符合协议 3000 m 以下" / "未收到进程单"）。

## 7. 间隔标准分级与跑道状况（§160–§161、§288–§289、§406–§408）

### 7.1 现状与问题

```js
// js/domain/separation.js（现状）
export function horizontalStandardKm() {
    return state.defaults.minSeparationNm;   // ← 单一阈值，不区分席位
}
```

规章 §406 明确区分**进近 5.6 km / 区域 9.3 km**，且区分**雷达/非雷达**与**边界协调与否**。
现状的"一个数管所有"既不真实，也丢掉了"进近比区域更紧"这一重要的玩法张力。

### 7.2 分级间隔标准（§406）

| 场景 | 规章要求 | 游戏内常量 | 备注 |
|---|---|---|---|
| 雷达管制 · 进近 | ≥ **5.6 km** | `SEP_APP_RADAR_KM = 5.6` | 终端区（APP 席位） |
| 雷达管制 · 区域 | ≥ **9.3 km** | `SEP_AREA_RADAR_KM = 9.3` | 区调席位（ACC） |
| 相邻管制区边界 · **未经协调** · 雷达 · 进近 | ≥ **2.8 km** | `SEP_APP_RADAR_UNCOORD_KM = 2.8` | 边界"边缘"标准 |
| 相邻管制区边界 · 未经协调 · 雷达 · 区域 | ≥ **4.7 km** | `SEP_AREA_RADAR_UNCOORD_KM = 4.7` | 同上 |
| **非雷达** · 进近 | ≥ **5.6 km** | 同 `SEP_APP_RADAR_KM` | 数值相同，但**判定路径不同**（无雷达更新率保障） |
| **非雷达** · 区域 | ≥ **9.3 km** | 同 `SEP_AREA_RADAR_KM` | 同上 |
| 塔台（机场管制） | 由跑道/尾流/刹车效应决定 | `SEP_TWR`（规则复合） | §408 见 §7.5 |

**实现**（`domain/separation.js` 扩展，保持向后兼容）：

```js
/** 分级间隔标准（km）：按航空器所属席位 + 雷达/协调状态解算 */
export function standardKmFor(ac, ctx = {}) {
    const unit = ac.unit || 'ACC';
    const radar = ctx.radarControl !== false;
    const uncoordinated = !!ctx.boundaryUncoordinated;
    if (unit === 'TWR') return towerStandardKm(ac);
    if (unit === 'APP') return uncoordinated ? SEP_APP_RADAR_UNCOORD_KM : SEP_APP_RADAR_KM;
    return uncoordinated ? SEP_AREA_RADAR_UNCOORD_KM : SEP_AREA_RADAR_KM;
}

/** 兼容旧 API：无席位上下文时回退到设置值（v1.6 行为不变） */
export function horizontalStandardKm() {
    return state.defaults.minSeparationNm;   // 保留，标注 @deprecated（P6 移除）
}
```

> **迁移策略**：`predictedConflicts()` / `getConflictPairs()` 改为调用 `standardKmFor(ac, ctx)`；
> 当 `state.defaults.tieredSeparation !== true`（默认 **false**）时全部回退旧逻辑，
> 保证**现有 92 项冒烟断言不受影响**；P6 完成后把默认值翻转为 `true`，并同步更新断言。

### 7.3 进近 5 km 特批（§407）

规章允许在**满足 9 项条件**时把进近雷达间隔降到 **5 km**。本项目把它做成**可开关的高难/教学机制**：

| # | §407 条件 | 游戏内检查 |
|---|---|---|
| 1 | 跑道末端 18.5 km 内同航迹 | 进近轨迹在同一航向容差内 |
| 2 | 平均跑道占用 ≤ 50 s | 跑道占用统计 ≤ 50 s |
| 3 | 刹车效应"好" | `runway.brakingAction === '好'`（§288 六等级） |
| 4 | 雷达方位精度 ≤ 0.3° 且更新 ≤ 5 s | `state.equipment.radar` 等级（示意字段） |
| 5 | 能目视或场面监视跑道及进出滑行道 | 塔台视景窗交互点已使用 / 场面监视正常 |
| 6 | 不违反尾流间隔 | 尾流规则检查（本项目简化为"重型后接轻型 → 禁 5 km"） |
| 7 | 密切监视进近速度 | HUD 速度监视开启（示意开关） |
| 8 | 驾驶员尽快退出跑道 | 落地后 `exitRunwaySec` 统计 |
| 9 | 航情资料已公布 | 关卡数据标记 `published: true` |

9 项全绿时，`reducedApproachStandard` 才可开启 → 进近间隔降为 `SEP_APP_REDUCED_KM = 5.0`。
**任何一项转红 → 自动回退 5.6 km 并通报**（这条"自动回退"本身是很好的教学点）。
默认**关闭**，因为它需要 §23 的"运行变更"批准——游戏内表现为"教学关卡的进阶挑战"。

### 7.4 平行跑道起飞（§408）

| `parallel:deviation` | `{ ac, angleDeg, atKm }` | HUD 告警、评分、复盘 |

**验收（Step R2，≈12 项断言）**：`standardKmFor` 对 APP/ACC/TWR 分别返回 5.6/9.3/塔台规则；
边界未协调时降为 2.8/4.7；非雷达路径与雷达路径数值一致但标记不同；
`tieredSeparation=false` 时全部回退旧值（**回归保护**）；5 km 特批 9 条件任一不满足即不可开启；
条件转红自动回退 5.6 km 并通报；刹车六等级到系数的映射单调；
同跑道先后起飞的 15°/2 km 两条检查触发；跑道检查中禁用起降许可；
ATIS 通播第 7 项为跑道表面状况。

## 8. 执勤疲劳硬指标对照（§123–§128）

### 8.1 口径定义（严格对齐 §123–§125）

本规则把"人待多久"拆成三个口径，本项目**照搬这个三分法**，因为它们回答三个不同问题：

| 口径 | 规章定义（§123–§125） | 本项目字段 | 回答什么问题 |
|---|---|---|---|
| **执勤时间** `duty` | 从**报到**到**完成工作**，含岗前准备、岗位执勤、岗后讲评、培训、其他 | `dutySec` | "这个人今天上了多久班" |
| **岗位执勤时间** `position` | 从**到达岗位**到**离开岗位** | `positionSec` | "这个人在席位上指挥了多久" |
| **休息时间** `rest` | 从**到达休息地点**到**离开**，期间**不应安排任何工作** | `restSec` | "这个人真正休息了多久" |

三者的关系：`dutySec ≈ prepSec + positionSec + debriefSec`（含培训/其他项时更长），**`restSec` 不计入 `dutySec`**。
值班面板（`ui/rosterPanel.js`）三段分别显示，复盘时间轴按口径着色。

> **为什么照搬**：玩家最容易误解"坐着不动的时间才算工作"。§123 明确**岗前准备和岗后讲评都算执勤**，
> 这条恰好能支撑 WORKPLACE §4 的 `PREP` / `DEBRIEF` 两个阶段——它们不是装饰，是**计入工时的真实环节**。

### 8.2 硬指标双栏对照

左栏为本规则原文口径，右栏为本项目的**游戏化压缩**。所有压缩值进 `data/roster.js`，**不硬编码**。

| # | 规章硬指标（§127） | 本项目（整班模式） | 压缩比 / 说明 |
|---|---|---|---|
| ① | 连续执勤 **≤ 10 h** | 一段班次累计 `dutySec ≤ SHIFT_DUTY_MAX`（示意 **60 min** 实时） | 10 h → 60 min，约 **1:10**（可调） |
| ② | 连续 24 h 内执勤 >10 h 者，须在累计到 10 h **之前**提供 **≥连续 8 h 休息** | 超过 `DUTY_EXTENDED_THRESHOLD`（示意 40 min）前，必须已进入一次 `RESTING`（示意 ≥5 min） | 8 h → 5 min，约 **1:96**（可调） |
| ③ | 1 个日历周执勤 **≤ 40 h** | **周模式**：7 个"交易日"累计 `dutySec ≤ WEEK_DUTY_MAX`（示意 180 min） | 40 h → 180 min，约 **1:13** |
| ④ | **管制席连续岗位执勤 ≤6 h**；**雷达管制连续岗位执勤 ≤2 h，两次岗位执勤间隔 ≥30 min** | `positionSec ≤ 6 h` 对齐为 `POSITION_MAX`（示意 30 min）；**雷达席位每 ≥2 min 强制轮换**（`RADAR_ROTATION_SEC`），休息 ≥30 s（`RADAR_BREAK_MIN_SEC`） | 6 h → 30 min（1:12）；2 h → 2 min（1:60）；30 min → 30 s（1:60） |
| ⑤ | 任意连续 **7 个日历日内**至少 **1 个 ≥连续 24 h 休息期**（或任一日历月内相当时间） | 周模式下第 6 个交易日收班后进入 `WEEKLY_REST`（示意不收班，只播报"已满足周休息期"） | 仅**数据满足 + 播报**，不做 24 h 空档 |
| ⑥ | 每个日历年至少一次 **≥连续 5 日休息** | 年度条（`ANNUAL_REST`）：累计通关 X 班后触发一次"年假"叙事，**不锁玩法** | 纯叙事 / 成就，不影响可玩性 |
| ⑦ | 不可抗力、应急情况下超时，条件允许时应**及时补休**；超出部分**计入下一执勤时间** | 应急事件（§9）导致超时 → 记 `DUTY_OVERFLOW` 并顺延到下一班次的 `dutySec` 起点 | 对齐（只是时间被压缩） |

> **⚠ 最重要的取舍（回指 WORKPLACE §5.2）**：**疲劳只影响玩家的操作精度，不改世界状态**。
> 规章要求的是"不得安排疲劳管制员执勤"，本项目把它翻译成——
> 疲劳升高 → 错诵率上升 / 用语被精简 / 响应时限收紧 → 系统**提示并强制轮换**，
> **但绝不代替玩家制造事故**。原因是：如果疲劳会自己产生事故，玩家就无法通过操作挽回，
> 惩罚变成不可控的随机性，教学价值反而归零。详见 WORKPLACE §5.2 与 §11 风险取舍。

### 8.3 §126 / §128：上报与"不适任"

| 规章要求 | 本项目机制 | 落点 |
|---|---|---|
| §126 疲劳**无法继续**工作时应**及时报告**；单位不得继续安排其执勤 | `REST_DUE` 事件 + HUD 提示"建议申请离席"；玩家可主动申请 → `NOT_FIT_FOR_DUTY`（**不扣分**）；超时未离席才记 `REST_IGNORED`（扣分） | `game/workplace.js`、`game/scoring.js` |
| §128 不得参加岗位执勤 4 种情形 | `PREP` 面板自评 4 项（体检/饮酒与药物/执照权利/其他），任一为"是"→ 本班直接进入 `DEBRIEF` 且**不记失败**，只记 `NOT_FIT_FOR_DUTY` | `ui/prepPanel.js` |

**四条不适任**在本项目中一律处理为"**这是你的职业判断，游戏尊重它**"：
不对"我今天不适任"做道德评价或分数惩罚——这与 §1.2「可玩优先」和"教学口径正确"并不冲突，
反而正是现实规章的态度（§126 明确把"报告"设为**正确行为**）。

### 8.4 数据、事件与验收

**数据**：新增 `data/roster.js`，字段与默认值（全部可调）：

```js
// data/roster.js —— 示意值，非真实依据
export const ROSTER = {
  mode: 'short',                 // 'short'（现状，单班剧情）| 'full'（整班制度）
  shiftMode: 'single',           // 'single' | 'weekly'
  dutySecMax: 3600,              // ① 连续执勤上限 → 60 min
  dutyExtendedThresholdSec: 2400,// ② 超过则必须先休息
  dutyExtendedRestSec: 300,      // ② 强制休息时长 → 5 min
  weekDutySecMax: 10800,         // ③ 周一班累计 → 180 min
  positionSecMax: 1800,          // ④ 管制席连续岗位执勤 → 30 min
  radarRotationSec: 120,         // ④ 雷达管制连续岗位执勤 → 2 min
  radarBreakMinSec: 30,          // ④ 两次岗位执勤间隔 → 30 s
  weeklyRest: true,              // ⑤ 播报而非空档
  annualRest: true,              // ⑥ 叙事 / 成就
  fatiguePerDutySec: 1 / 3600,   // 疲劳增长斜率（示意）
};
```

**事件**：`duty:started` / `duty:ended` / `duty:overflow` / `position:entered` / `position:left` /
`rest:entered` / `rest:left` / `radar:rotation_due` / `fatigue:threshold` / `not_fit_for_duty`。

**验收（Step R1，≈10 项断言）**：

1. `dutySec` 覆盖 `PREP + ON_POSITION + DEBRIEF` 三段（不只是坐席时间）；
2. `restSec` **不计入** `dutySec`；
3. `dutySec` 超过 ① 上限即触发 `duty:ended`（班次收束，不静默继续）；
4. ② 未先休息就跨越 `dutyExtendedThresholdSec` 时告警，且不能继续累计到 ① 上限；
5. 雷达席位 `positionSec` 达 `radarRotationSec` 必触发 `radar:rotation_due`；
6. 轮换间隔不足 `radarBreakMinSec` 时不允许立即重新就座（旁位监督除外）；
7. 休息期内**所有指挥入口被禁用**（含远程接管入口），只留"返回岗位"；
8. `mode:'short'`（默认）时以上全部按**既有 v1.6 行为**运行（**回归保护**）；
9. `NOT_FIT_FOR_DUTY` 不产生失败判定，只记录事件；
10. 同 seed 下疲劳曲线与轮换节奏可复现。

## 9. 应急预案与安全保卫（§31–§35、§42–§43）

### 9.1 六要素预案模板（§32）

§32 要求预案针对**设备失效**与**人员丧失能力**两类情形，明确管制员应遵循的基本程序，且至少包含 6 项内容。
本项目把它做成 `data/emergencyPlans.js` 的**六段脚本模板**：每一段都是一个可播放、可检查、可复盘的阶段。

| # | 规章六要素（§32） | 本项目段落 | 玩家要做什么 |
|---|---|---|---|
| ① | 组织体系与职责分工 | `roles` | 面板显示"现在谁负责什么"（领班 / 邻扇区 / 你） |
| ② | **空域应急接管方案** | `takeover` | 邻扇区 AI 接管你的部分空域；确认接管范围 |
| ③ | 保证安全的具体措施 | `safety` | 暂停新进港 / 扩大间隔 / 限制目视进近（按事件类型给 1–3 项） |
| ④ | 管制员操作程序 | `controller` | 按检查单逐项执行（话术 + 动作），支持"漏项 → 复盘标注" |
| ⑤ | **恢复空中交通服务的程序** | `recovery` | 逐步恢复：解除限制 → 恢复进港 → 恢复常规间隔 |
| ⑥ | 与相关单位协调配合机制 | `coordination` | 通报相邻单位 / 机场 / 气象（可自动可手动） |

**设备失效**与**人员丧失能力**两类各给一个脚本范例：

| 情形 | 触发 | ①②③④⑤⑥ 摘要 |
|---|---|---|
| 雷达 / 通信设备失效 | `equipment:failure` | 邻扇区接管 → 立即扩大间隔 → 转程序管制（话术模板）→ 通知设备部门 → 逐级恢复 → 通报邻区 |
| 管制员（AI 同事或你）丧失能力 | `incapacitated` | 旁位接管 → 冻结新指令 → 已发出的许可逐条确认 → 领班到场 → 恢复服务 → 记录与讲评 |

> **游戏化处理**：这两类事件都不产生"无法挽回的事故"。玩家可以在压缩时间尺度内完成整套处置；
> 失误只影响评分与复盘（"你在第 ③ 步漏了暂停新进港，导致恢复阶段多了一个冲突"）。

### 9.2 讲评与预案修订（§34）与演练（§35）

| 规章要求 | 本项目机制 | 落点 |
|---|---|---|
| §34 处置完成、恢复正常服务后应**分析评估、总结经验、修订预案** | `DEBRIEF` 新增"规章视角"页：显示**本次走了哪几段、漏了哪一段**；玩家可点"修订预案"给 `data/emergencyPlans.js` 的该条脚本打一个本地标记（**仅影响本机难度提示，不上传**） | `ui/debriefPanel.js` |
| §35 应对管制人员做应急预案**培训**并**定期组织应急演练** | **演练模式 `drill`**：不接真实流量，按脚本走一遍六要素，逐段打分；可由领班在班中随机安排（`supervisor:drill` 事件） | `game/scenario.js`（场景开关）、`game/director.js`（排程） |

**演练模式的三条约束**（保证不破坏主玩法）：

1. 演练**独立于主线进度**，可随时开始/中途退出，退出不扣分；
2. 演练中世界**不推进真实航班**（或用"假航班"占位），因此不会因为练手而丢掉架次；
3. 演练结果进"训练记录"，**不计入运行评分**——现实里演练与运行也不是同一本账。

### 9.3 安全保卫（§42–§43）

| 规章要求 | 本项目机制 |
|---|---|
| §42 防止损害；对有意或无意损害的应对；**防止未经许可人员进入管制单位** | 现场层"门禁"状态：`badge:check`（进入管制室）、`visitor:alert`（未登记人员闯入）作为**现场突发事件**（WORKPLACE §7.2 清单已预留） |
| §43 外来人员 6 项（①合理理由并事前申请 ②履行批准手续 ③证件登记 ④工作人员陪同 ⑤不得干扰运行 ⑥遵守安保制度与程序） | 访客流程做成 **6 步交互单**（`ui/visitorPanel.js` 可选模块）：缺任一步 → 领班提示"请先完备手续"。**不扣运行分**，只影响现场秩序评价 |

> **刻意不做**：外籍人员报批、涉密任务、重大运输任务期间的额外限制（§43 后半段）——
> 这些涉及真实敏感场景，本项目**只做"访客登记 + 陪同"这类通用教学点**，其余不实现（回指 §1.3 合规边界）。

### 9.4 数据、事件与验收

**数据**：`data/emergencyPlans.js`（六段模板，每段含 `id / title / checklist / timeoutSec / scoreWeight`）；
`data/visitor.js`（6 步清单，可选）。

**事件**：`emergency:started` / `emergency:step_done` / `emergency:step_missed` / `emergency:recovered` /
`drill:started` / `drill:finished` / `visitor:alert` / `badge:check`。

**验收（Step R3，≈10 项断言）**：

1. 每个预案脚本恰好含 6 段，段 id 与 §32 六要素一一对应；
2. 缺任一段时不允许标记 `emergency:recovered`；
3. 设备失效与人员丧失能力两条脚本都能走通（含"邻扇区接管"）；
4. 接管期间原席位指令入口按 WORKPLACE §5.5 的"空岗"规则处理；
5. `DEBRIEF` 的"规章视角"页能指出漏掉的段落编号；
6. 演练模式不改变主线评分与航班进度；
7. 演练可重入、可中途退出且不扣分；
8. 访客 6 步缺一步即提示，且**不影响运行评分**；
9. 未登记人员闯入触发 `visitor:alert` 并暂停现场层移动（不是暂停指挥）；
10. `emergencyPlans.js` 缺字段时在**加载期**报错，不进入运行期（数据校验前移）。

## 10. 管制运行记录与日志（§62–§69）

### 10.1 五类记录（§62）与九项工作日志（§63）

§62 要求记录 5 类内容，§63 进一步规定**管制工作日志至少包含 9 项**。本项目把"记录"变成
**运行期低开销 + 复盘期高价值**：运行期只往事件总线投事件，复盘期再聚合成人类可读的日志页。

| §62 五类 | 本项目对应 | 产生方式 |

| 重要数据记录 | 间隔标准变化、跑道状况、ATIS 通播版本 | `separation:*` / `runway:*` / `atis:*` |
| 飞行计划与进程单 | 航班生成、进程单状态、许可与复诵 | `flight:*` / `clearance:*` / `readback:*` |
| 活动统计 | 架次、延误、冲突、复飞、评分构成 | 复盘聚合（不逐条存） |

**§63 九项工作日志 → `data/logFields.js` 字段表**：

| # | 规章九项 | 字段 | 数据来源 |
|---|---|---|---|
| ① | 席位开放与关闭 | `seatOpenLog[]` | `seat:opened` / `seat:closed`（§3.3） |
| ② | 岗位人员工作及准备 | `staffLog[]` | `duty:started` / `position:entered` / `prep:done` |
| ③ | 值班时间与交接班 | `dutyLog[]` | `duty:*` 三段计时 + `handover:*`（§4.3） |

### 10.2 保存分级（§64–§67）

| 规章保存要求 | 本项目 | 说明 |
|---|---|---|
| §64 重要数据 **≥30 天**（地空语音、平面通信、数据链、监视数据、航迹标牌、电子进程单） | 存档内**结构化事件**保留最近 30 个"交易日"（超出滚动丢弃） | 本项目无真实语音，做**结构化等价物** |
| §65 文本记录 **≥30 天**（飞行计划、进程单、自动通播、工作日志） | 工作日志 + ATIS 版本 + 进程单快照保留 30 个交易日 | 同上 |
| §66 **≥6 年** 6 项（服务中断、设备故障、设施不可用、**管制员岗位执勤记录含岗前准备**、不安全事件、运行手册） | 存档分为两层：`session`（本局明细）与 `career`（长期档案）；`career` 只保留 §66 六类的**汇总条目**，**不设自动过期** | 6 年 → 永久保留（更保守，不违反） |
| §67 事故相关记录**长期保存** | `safetyLog` 中标记 `serious:true` 的条目永久保留 | 对齐 |
| §68 日常统计应按规定上报 | **不做上报**（本项目无上级单位概念） | 主动偏离，见 §10.4 |

### 10.3 §69 合规边界（本项目最重要的一条硬约束）

> **§69：管制运行记录不得用于商业目的；未经所属法人同意不得对外提供。**

本项目据此确立三条**不可协商**的约束：

| 约束 | 实现 |
|---|---|
| **不采集** | 不接入任何真实管制系统、不读取真实运行数据、不做屏幕/话音抓取 |
| **不上传** | 全部日志只写本机存档；**无遥测、无崩溃上报、无第三方统计 SDK** |
| **不对外提供** | 无导出到服务端的路径；导出功能（若做）只导出**玩家自己的练习数据**，并由玩家手动触发 |

游戏内的"运行记录"在语义上**始终是玩家练习数据**，不是任何真实管制单位的运行记录。
存档页面与导出的文件头部都带一行声明：**"本文件为模拟练习数据，非真实管制运行记录。"**

### 10.4 数据、事件与验收

**数据**：`data/logFields.js`（九项字段表 + 每项对应事件名）；`data/retention.js`（30 天 / career 永久的分类规则）。

**事件**：`log:appended`（低开销，仅记关键字段）/ `log:rolled`（超出保留窗口）/ `archive:packed`（收班归档）。

**验收（Step R1 + R3，≈8 项断言）**：

1. §63 九项**全部**有对应字段与事件，缺一项即失败；
2. 日志字段只增不改（用字段快照断言）；
3. 保留窗口滚动时，超出 30 个交易日的明细被丢弃，`career` 六类汇总不受影响；
4. `serious:true` 的安全事件不会被滚动丢弃；
5. 存档头含"模拟练习数据"声明；
6. 代码库中**不存在**任何网络上报调用（静态检查：无 `fetch` / `XMLHttpRequest` 指向遥测端点）；
7. 导出功能只导出本地存档，且导出前弹一次确认；
8. `data/logFields.js` 缺字段在加载期报错。

## 11. 实施步骤与验收

本文提出的机制**不单独成为一个版本**，而是作为"规章对齐"贯穿 Workplane 的 Step R1–R3，
每一步都可以独立交付、独立验收。

| **R2** | v2.2 | 移交与协议（§5）+ 许可与复诵（§6）+ 间隔分级与跑道状况（§7） | `domain/handoff.js`、`domain/priority.js`、`data/agreements.js`、`data/atis.js` | ≈10 + 12 + 12 = **34 项** |
| **R3** | v2.3 | 应急预案与演练（§9）+ 讲评页（§9.2）+ 访客/门禁（§9.3）+ 存档归档（§10.4） | `data/emergencyPlans.js`、`data/retention.js`、`ui/debriefPanel.js`、`ui/visitorPanel.js` | ≈10 + 8 = **18 项** |

**总计 ≈78 项新断言**（现有 92 项保持不变，合计约 170 项）。

**依赖顺序**：

```
R1 席位/制度/疲劳/日志  ──►  R2 移交/复诵/间隔  ──►  R3 应急/档案
        （人员与席位就位）        （规则与话术就位）        （兜底与留痕就位）
```

**与 WORKPLACE Step W1–W3 的关系**：两套步骤**并行不冲突**——
W 系列建"现场与人在哪"，R 系列建"制度与规则怎么算"。
共享的落点是 `data/roster.js`（W2 与 R1 都要用）与 `data/workspaces.js`（W1 与 R1 的席位表）。
建议实现顺序：**W1 → R1 → W2 → R2 → W3 → R3**（先有可坐的席位，再谈制度）。

**回归保护（贯穿三步）**：所有新机制默认关闭或默认走旧路径——
`ROSTER.mode:'short'`、`tieredSeparation:false`、`drill` 不启用、`logFields` 只写不读。
`npm run check` 与 `npm run smoke` 的现有断言**必须全部保持 PASS**。
